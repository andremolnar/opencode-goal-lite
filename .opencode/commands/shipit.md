Ship the current, explicitly identified work in this repository. Extra instructions: $ARGUMENTS

Adapted from andrebot's `/shipit`. Work in this session and follow repository conventions. Do not treat this prompt as permission to include unrelated changes or bypass checks.

1. Inspect the current branch, upstream, remotes, `git status --short`, staged and unstaged diffs, untracked files, and recent commits. Identify which files belong to this work. This repository may already contain unrelated work: if ownership is uncertain, ask before staging or committing. Never stage with `git add -A` or `git add .`; never stage secrets, credentials, `.env*`, local OpenCode config, generated `dist/`, or unrelated files. Do not modify or discard someone else's changes.
2. Check gate *configuration* before shipping: `package.json` must have real `check`, `build`, and `test` scripts; a repository-owned pre-commit hook must run staged formatting (if configured), type checking, and tests; and a CI workflow for the target branch must run at least type checking, build, and tests on a clean install. Check the actual files and commands rather than assuming an installed skill or a passing local run means the hook/CI exists. If any gate is missing, use the `setup-pre-commit` skill as guidance for hook setup (adapt its `typecheck` step to this repo's `npm run check`), and add/repair CI as appropriate for this repository. **Do not follow that skill's automatic stage-and-commit step**; use the explicit scoping and approval rules here. If gate setup is outside the user's authorized scope or cannot be completed, stop and report the missing gate; do not describe the work as shipped. Do not skip hooks with `--no-verify` or equivalent.
3. Load and apply `changelog-entries` to create/update `CHANGELOG.md` with user-facing outcomes for the changes being shipped, following existing versioning conventions. If there is no changelog or no clear release version, propose the lowest-risk version and ask for confirmation before choosing a release version; do not invent a published release. Check whether README or decision documentation needs updating as a result of this work, and update only when justified.
4. Run the configured formatting/lint check if present, then `npm run check`, `npm run build`, and `npm test`. Run any other relevant project-specific checks. Fix failures within scope and rerun; if a failure is outside scope, stop and report it. Inspect `git diff --check`, status, and all intended staged content for accidental changes, secrets, and changelog accuracy. Ensure the proposed CI and hook checks are executable, not just present on disk. A local run is not proof that remote CI passed; if CI cannot be observed, say it is pending.
5. Stage only the agreed files, including the relevant changelog and gate configuration. Inspect `git diff --cached --stat` and `git diff --cached` (including new files) before committing. Load and apply `kick-ass-commit` to draft a specific, factual subject and body that explain what changed and why, based on the staged diff. Do not include claims of checks that were not run. Commit only if the staged diff is nonempty; let hooks run. Verify the final message with `git log -1 --format=%B` and the committed files with `git show --stat --oneline HEAD`. If a pre-commit hook changes files or fails, resolve and revalidate before committing; never silently bypass it.
6. Push or open a PR only when the user explicitly authorized that remote action for this work (in `$ARGUMENTS` or the conversation). Confirm the intended remote/branch and target, never force-push or push directly to a protected branch without explicit authorization, and prefer a PR against the default branch. If authorization, remote, authentication, or CI confirmation is missing, stop at a local commit (or earlier if a required gate is missing) and give exact next steps. Do not merge, publish a package, tag a release, or assert CI is green unless separately authorized and verified.
7. Report what was committed, the branch and commit SHA, the changelog entry, each gate and its observed result, and any pending CI/PR/push action. Say "shipped" only when the authorized remote handoff actually happened; otherwise state precisely where the process stopped.
