# Craft a Goal Lite contract

Use the user's request as the source of truth. The contract helps an agent work; it must not invent authorization, requirements, or proof.

Scope "done" to work the agent can actually deliver. Human PR approval, merge, and deployment in another environment are handoff steps, not default Goal Lite completion gates. If the user explicitly includes them in the goal, distinguish what the agent can finish from what remains with a human; do not mark an unmet criterion done to satisfy structural readiness.

1. Read the request and call `tools.goal.status` first. If a goal already exists in this session, do not call `tools.goal.start` again: edit an active goal only as requested, or use a new session for a completed goal. If Goal Lite is unavailable or status reports a setup diagnostic, show the contract as a draft and report the prerequisite; do not claim it was persisted. If the user only wants a draft, do not start a goal.
2. Identify the request's scope before searching. Locate the active project's applicable ADRs and PR/code-review guidance using repository instructions and a bounded filename/content search. Read only sources relevant to this scope. Do not assume a directory layout, ADR numbering, branch names, required commands, or a universal approval process. If guidance is missing or contradictory, report that rather than inventing it. Keep relative file paths for later reference; do not copy entire policies into goal text.
3. Extract a one-sentence **objective** describing the desired outcome, not the implementation method. Preserve the user's terms and boundaries. Separate explicit requirements from reasonable assumptions.
4. Write 1–7 **success criteria** as observable outcomes; use only as many as distinct outcomes require. For each, name what an observer could inspect or experience and the smallest convincing evidence. Include functional behavior, relevant error/safety paths, and documentation or integration only when they matter to the request. If a PR handoff is in scope, an open PR and no **known** P0/P1 (or equivalent blocking) findings after applicable checks/review can support "ready for human review"; do not assume every project uses those severity labels or that the plugin can prove no issues exist. Do not turn human approval or merge into an implicit criterion. A passing test is evidence for its own coverage, not proof of unrelated behavior. Avoid criteria like “do a good job,” “all tests pass,” or “the agent says it is done” unless the user specifically requires them.
5. Write **constraints** as hard boundaries (must not do, must preserve, environment, authority, safety). Carry forward every explicit user constraint and applicable project policy. Do not turn preferences into mandatory prohibitions or add every project quality gate as a goal-specific constraint. When a constraint needs human judgment, say so; Goal Lite's review note is an attestation, not independent enforcement.
6. Draft a short, ordered **task list** of next steps, marked required unless clearly optional. Tasks are a working plan, not additional success criteria. Grow, shrink, block, reopen, or reorder them as discoveries warrant; removal requires a reason and does not count as completion.
7. Check for conflicts, unverifiable historical claims, invented scope, missing authorization, and impossible-to-demonstrate acceptance. If a single ambiguity would materially change the goal, ask one focused question with a safe recommendation. Otherwise state a narrow assumption and proceed; do not create an approval loop.
8. Show a concise contract (objective, numbered criteria, constraints, tasks, assumptions, relevant policy references) before recording it. If the user explicitly asks to start a goal (including `/goal`) and gives enough detail, call `tools.goal.start` in the **same session** using short stable IDs (`outcome-1`, `safety-1`, `step-1`) and the documented `objective`, `criteria`, `constraints`, `tasks` input shape. Then save discovered relative paths with `tools.goal.update({ expectedRevision, change: { type: "policy.set", adrs: [...], review: [...] } })`; empty lists are honest when no sources were found. If the active tool snapshot rejects `policy.set`, report that references were not saved and that recovery after compaction remains unverified for this goal; do not silently imply persistence or overwrite an existing goal.
9. Work from the recorded goal. After compaction, call `tools.goal.status` to recover the exact contract and any saved policy references. Revisit relevant sources when scope changes, guidance is stale or conflicting, or work approaches code review; do not reread the whole ADR corpus on every turn. Update saved references if they change. Record criterion evidence only after observing it and review constraints explicitly. Before `tools.goal.finish`, compare each criterion to the actual work and evidence, check unresolved **in-scope, agent-actionable** blockers and applicable pre-handoff checks; keep unmet criteria or required tasks open even if structural readiness says ready. A required independent pre-handoff review is not satisfied by self-review. If the agent's work is complete but a human must review, approve, merge, or deploy, finish with a candid handoff summary rather than waiting for that external action—unless the human outcome is an explicit, unmet criterion. Call it "ready for human review" only if the PR is actually open (when that is the project's handoff route) and no P0/P1 or equivalent blocking issues are known; otherwise say precisely what handoff is pending. Goal completion is an agent attestation, not independent proof or merge approval. Do not rerun tests to satisfy bookkeeping.

If the request is empty, ask for the desired outcome before inventing a contract. Never store secrets in goal text, evidence, or policy references.
